# AI 代码追踪系统：让机器生成的代码无处遁形

在软件开发进入 AI 辅助时代的今天，一个新的问题摆在了我们面前：当项目中既有程序员手写的代码，又有 AI 生成的代码时，我们如何准确地知道哪些代码出自 AI 之手？这个问题看似简单，实则关系到代码审查、质量评估、团队协作等诸多方面。本文将介绍一个完整的 AI 代码追踪系统，它能在代码产生的瞬间就为其打上"身份标签"，让每一行代码的来源都清晰可追溯。

## 系统的核心思想

这个系统解决问题的方式相当直接：既然我们想知道哪些代码是 AI 生成的，那就在 AI 生成代码的那一刻把它记录下来。听起来简单，但在实际实现中却需要巧妙的设计。

想象一下日常的开发场景。程序员小李正在使用 Cursor 编辑器写代码，遇到一个排序算法的需求，他按下快捷键呼唤 AI 助手："帮我写一个快速排序函数。" AI 思考片刻后生成了代码，小李看了看，觉得不错，点击了"应用"按钮。就在这个瞬间，系统开始工作了。

Cursor 编辑器在设计时预留了一些"钩子"，就像是在特定时刻会被触发的陷阱机关。当小李点击"应用"时，一个名为 stop 的钩子被触发，它会精确地捕获到这次 AI 生成的所有信息：生成了哪些代码、用的是什么 AI 模型、在哪个文件的什么位置。这些信息会被立即压缩并发送到后端服务器存储起来。

这种实时捕获的方式有一个巨大的优势：它不需要去猜测代码是谁写的，因为捕获动作本身就发生在 AI 生成的那一刻。就好比监控摄像头恰好拍到了犯罪现场，证据确凿，无需推理。

## 深入技术实现的三个层次

整个系统可以分为三个层次来理解：插件层、后端层和前端层。它们各司其职，构成了一个完整的追踪链路。

### 第一层：插件层的捕获机制

插件层运行在 Cursor 编辑器内部，它是整个系统的眼睛和耳朵。在 Cursor 编辑器的配置目录里（通常是用户主目录下的 .cursor 文件夹），有一个 hooks.json 配置文件。这个文件告诉 Cursor：当某些事件发生时，请执行这些脚本。

最核心的脚本是 stop.js，它在每次 AI 生成结束时被调用。Cursor 会通过标准输入流向这个脚本传递一个 JSON 对象，里面包含了丰富的元数据：对话 ID、生成 ID、使用的模型名称、当前的工作目录等等。脚本收到这些信息后，会做一件至关重要的事情：获取 Git 差异。

你可能会问，为什么要获取 Git 差异？因为差异才是真正描述"代码变化"的东西。Git diff 命令能告诉我们：在哪个文件的哪一行，删除了什么内容，又添加了什么内容。这种格式化的差异信息是后续分析的基础。

但这里有个技术难点：如果开发者创建了一个全新的文件，Git 默认不会把它包含在差异中，因为它还不在 Git 的追踪范围内。系统使用了一个巧妙的方法：先用 git add -N 命令把新文件临时添加到暂存区（但不真正添加内容），然后获取差异，最后再用 git reset 命令撤销这个临时操作。这样就能捕获到包括新文件在内的所有变化。

获取到差异后，脚本会把它压缩（使用 Gzip 算法）并编码成 Base64 格式。这是因为代码差异可能很大，压缩能节省传输带宽和存储空间。压缩后的数据连同所有元数据一起，通过 HTTP POST 请求发送到后端服务器。

### 第二层：后端层的存储与分析

后端是一个基于 Node.js 和 Express 框架构建的服务，它负责接收、存储和分析数据。数据存储在 SQLite 数据库中，虽然 SQLite 相对简单，但对于这个系统的需求来说完全够用。

当后端收到插件发来的数据后，它会做一些必要的处理：验证数据的完整性、解压缩差异内容、提取关键信息等。然后将这条记录插入数据库。数据库表的设计很直观：每条记录包含生成 ID、用户 ID、仓库地址、分支名称、使用的模型、压缩后的差异，以及创建时间等字段。

但存储只是第一步，更重要的是分析。后端提供了多个 API 接口，其中最核心的是代码归属分析接口。这个接口的工作原理值得详细说明。

假设程序员小王在一周的时间里，用 AI 生成了一些代码，也手写了一些代码，现在他想知道某个文件里每一行代码的来源。系统是这样工作的：

首先，它会从数据库中找出所有相关的 AI 生成记录。每条记录包含的差异数据会被解压并解析，提取出所有"新增"类型的代码行。对每一行代码，系统会计算一个哈希值。这个哈希值是通过对代码内容（去除首尾空格后）进行 SHA256 计算得出的，然后取前 16 个字符。哈希值的作用是作为这行代码的"指纹"。

接下来，系统会通过 Git 命令获取目标文件当前的完整内容，同样按行分割。对当前文件的每一行，系统也计算它的哈希值，然后去查找：这个哈希值在 AI 生成记录中存在吗？如果存在，说明这行代码是 AI 生成的；如果不存在，说明这行代码是人工编写的。

这种基于内容哈希的匹配方式有一个巨大的好处：它不依赖行号。当程序员在文件中间插入了一行注释，所有后续代码的行号都会发生变化，但内容哈希不会变。系统依然能准确识别出哪些代码来自 AI。

举个具体的例子。假设 AI 生成了这样一个函数：

```javascript
function sleep(ms) {
    return new Promise(resolve => setTimeout(resolve, ms));
}
```

系统会为第二行代码计算出一个哈希值，比如 "a3f5e9d2b1c8..."。这个哈希值被存储在数据库中。后来，程序员在第二行上方插入了一行注释：

```javascript
function sleep(ms) {
    // 等待指定的毫秒数
    return new Promise(resolve => setTimeout(resolve, ms));
}
```

现在 Promise 那行的行号从 2 变成了 3，但它的内容没变，所以哈希值还是 "a3f5e9d2b1c8..."。系统通过匹配哈希值，能够准确识别出这行代码仍然是 AI 生成的。

### 第三层：前端层的可视化呈现

前端是用户与系统交互的界面，它使用 React 框架构建，提供了直观的可视化展示。整个前端分为两个主要页面：项目列表页和文件详情页。

项目列表页展示了所有被追踪的项目，每个项目显示仓库名称、分支、作者、AI 代码占比等信息。这个页面还支持一个特殊的功能：分支差异统计。用户可以输入本地仓库的路径，系统会计算当前分支相对于主分支的差异，然后统计这些差异中有多少是 AI 生成的。这对于代码审查很有用，比如在合并代码前，团队负责人想知道这个功能分支里有多少 AI 代码。

点击某个项目后，进入文件详情页。这个页面的左侧列出了所有变更的文件，每个文件旁边显示了新增、删除的行数，以及 AI 代码的数量。右侧则是代码的详细展示，这里用不同的颜色来标识代码的来源：绿色背景表示 AI 原始生成的代码，白色背景表示人工编写的代码。

文件详情页还支持一个强大的功能：commit 范围分析。用户可以选择两个 commit 点，系统会分析这两个 commit 之间的所有代码变更，并计算 AI 代码的占比。这个功能在查看某个时间段的开发效率时特别有用。

## 系统处理的核心难题

在实现过程中，系统解决了几个关键的技术难题，这些难题的解决方案体现了设计的精妙之处。

第一个难题是如何区分 commit 范围内外的代码操作。想象这样一个场景：在很早的一次提交中，AI 生成了一行代码；在最近的一次提交中，程序员删除了这行代码。如果我们只看这两次提交之间的差异，会发现一行 AI 生成的代码被删除了。但这里的关键是：删除操作是谁做的？

最初的实现版本会错误地认为这是"AI 删除"，因为被删除的代码确实是 AI 生成的。但这显然不对，删除这个动作是程序员做的，应该算作人工操作。修复后的版本采用了两遍扫描的策略：第一遍扫描找出在当前 commit 范围内被 AI 新增的代码；第二遍扫描时，只有那些在当前范围内被 AI 添加又被删除的代码才算"AI 删除"。如果一行代码在范围外就已经存在（无论是不是 AI 生成的），那么在范围内删除它就算人工操作。

第二个难题是大文件和大仓库的处理。当代码仓库很大，或者某次 AI 生成的代码量很大时，传输和存储都会成为问题。系统使用了 Gzip 压缩来解决这个问题，压缩后的数据通常能减少到原始大小的 10-20%。同时，在获取 Git 差异时，系统会过滤掉 node_modules 和 .git 这些不需要追踪的目录，避免产生巨大的差异数据。

第三个难题是工作目录的识别。插件脚本在运行时，它的当前工作目录是 Cursor 编辑器的安装目录，而不是用户项目的目录。如果直接用这个目录去执行 Git 命令，肯定会出错。解决方法是从 Cursor 传入的元数据中提取 workspace_roots 字段，这个字段包含了用户项目的真实路径。脚本使用这个路径作为 Git 命令的工作目录，就能正确获取项目的差异信息。

## 实际应用场景与价值

这个系统的价值体现在多个实际场景中。

对于个人开发者来说，它是一个自我认知的工具。当你回顾一周的工作时，你可以清楚地看到：这周写了 500 行代码，其中 200 行是 AI 生成的，300 行是自己写的。这种统计能帮助你更客观地评估自己的工作量和 AI 的辅助效果。

对于团队管理者来说，它是一个有力的管理工具。在代码审查时，审查者能看到哪些代码来自 AI，可以对这些代码投入更多的注意力，因为 AI 生成的代码可能存在理解偏差或者隐藏的问题。在评估团队效率时，管理者能知道 AI 工具对不同成员的帮助程度，从而做出更合理的资源分配。

对于开源项目维护者来说，它提供了一种新的透明度。当贡献者提交 PR 时，维护者能看到这个 PR 中有多少代码是 AI 生成的，这不是为了歧视 AI 代码，而是为了更好地理解代码的来源，从而给出更有针对性的审查建议。

系统的设计还考虑到了隐私保护。所有数据都存储在本地，不会上传到任何云端服务。代码内容经过压缩和哈希处理，即使数据库被人获取，也很难直接看到原始代码。用户完全掌控自己的数据，可以随时删除或导出。

## 系统的局限与展望

当然，这个系统也不是完美的，它有一些明显的局限性。

首先，它完全依赖 Cursor 编辑器的钩子机制。如果开发者使用其他编辑器（比如 VS Code 或 GitHub Copilot），系统就无法工作。这是因为不同编辑器的钩子机制不同，需要针对性地开发支持。

其次，它只能追踪"应用"了的 AI 代码。如果开发者让 AI 生成了代码，但看了看觉得不满意，没有点击应用按钮，这些代码就不会被追踪。虽然这些代码最终也没有进入项目，但在某些场景下（比如研究 AI 的拒绝率），这些信息也是有价值的。

再次，对于代码的"修改"，系统目前的处理还比较粗糙。它能识别出某行代码原本是 AI 生成的，后来被人修改了，但具体修改了什么、修改的程度有多大，这些细节还无法准确追踪。一个可能的改进方向是引入"相似度"的概念，用字符串相似度算法来量化修改的程度。

最后，系统目前只支持单人使用。在团队协作场景下，不同成员的追踪数据是分散的，没有一个中心化的聚合视图。要支持团队场景，需要设计更复杂的数据同步和权限管理机制。

展望未来，这个系统有很多可以扩展的方向。可以增加更多的统计维度，比如按模型类型统计（看看 GPT-4 和 Claude 哪个生成的代码更多被保留）、按时间段统计（看看一天中哪个时段最依赖 AI）、按文件类型统计（看看在前端代码和后端代码中 AI 的使用比例）等等。也可以增加更智能的分析功能，比如自动识别 AI 生成的代码中可能存在的问题模式，或者分析哪些类型的任务最适合交给 AI。

## 结语

AI 辅助编程已经成为现实，它极大地提升了开发效率，但也带来了新的管理挑战。这个 AI 代码追踪系统，通过在代码生成的源头进行实时捕获，为我们提供了一个准确、可靠的追踪方案。它让每一行代码的来源都清晰可见，为代码审查、效率评估、质量管理提供了数据支持。

更重要的是，这个系统体现了一种新的开发理念：承认 AI 的贡献，但不混淆人与机器的界限。它不是为了否定 AI 的价值，而是为了更好地理解和利用 AI。当我们知道哪些代码来自 AI 时，我们就能更有针对性地进行审查和优化，让人类的创造力和机器的效率完美结合。

在这个人机协作的新时代，我们需要的不是排斥 AI，也不是盲目依赖 AI，而是建立一套完善的机制，让每一次人机协作都有迹可循，让每一行代码都能找到它的出处。这个系统，正是朝这个方向迈出的一小步。
